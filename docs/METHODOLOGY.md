# 评测方法定义（METHODOLOGY）

本文件定义"怎么测、怎么算、怎么下结论"。代码必须实现这里的定义；定义的改动按 CLAUDE.md §2.5 处理。

每一节都写了**为什么**。面试时要讲的就是这些"为什么"，所以实现时不要把理由丢掉：结果文件和报告里要体现这些区分。

---

## 第零部分：五条总原则

所有后续定义都从这五条推出来。实现时遇到本文件没覆盖的情况，按这五条判断。

| # | 原则 | 为什么 |
|---|---|---|
| P1 | **最贵的错误是"看起来合理的错误数字"，不是崩溃** | 崩溃会被立刻发现；一个偏了几个百分点、格式正常的数字会被写进报告、被别人拿去决策。评测框架最常见的失败方式不是报错，而是安静地算错 |
| P2 | **拒绝胜过猜测** | 输入对不上（按位置关联、语料不同、缺少判分、标签不完整），就报错停下，不要输出一个"尽量对"的结果 |
| P3 | **区分三种结论：没修好 / 没测到 / 环境坏了** | 把环境故障算成被测系统失败，会让人去查一个不存在的问题；把没测到算成通过，更糟 |
| P4 | **每个数字都能追溯到产生它的代码和文件** | 报告里的数字由代码生成，不手写；结果文件带元数据 |
| P5 | **先测试你的测试** | 收集逻辑、评分员、验收用例本身都可能是错的。验收用例要先在已知有缺陷的输入上运行，确认它会失败 |

## 第一部分：记忆层评测

### 1.1 被测对象（arms）

| arm | 是什么 | 作用 | 是否需要 key |
|---|---|---|---|
| `null` | 什么都不存，检索永远返回空 | **对照组**。它的分数等于"答题模型只凭常识、题面措辞和选择题猜测能拿到多少"。其他 arm 都要读成"相对 null 的距离" | 否 |
| `bm25` | 本地关键词检索（如 rank_bm25），按消息切块 | 零成本的真实检索基线；CI 和 demo 都能跑 | 否 |
| `mem0` | 开源记忆框架 | 真实被测系统 | 是 |
| `everos` | 开源记忆系统 EverOS（Apache-2.0） | 真实被测系统；部署成本较高，作为可选 arm | 视部署而定 |

**为什么必须有 null**：EverMemBench 有 389 道选择题，随机猜就有约 25% 的正确率，而答题模型靠读选项推理还能拿得更高。不和 null 比，一个记忆系统的绝对分数几乎说明不了什么。

### 1.2 流水线

```
ingest（灌入语料）→ search（按题检索）→ answer（LLM 带检索结果作答）→ judge（判分）
```

每个阶段的输出落盘成 JSON，**后一个阶段只读前一个阶段的文件**，这样任何阶段都能单独重跑和审计。

每个结果文件必须带的元数据：
`corpus_id`（数据集版本 + 已灌入的天数范围）、`arm`、`arm_config_hash`、`answer_model`、`judge_model`、`judge_prompt_version`、`created_at`、`git_commit`。

### 1.3 证据窗口与筛题

语料通常只灌入一部分（例如前 N 天），但题目覆盖整个语料期。**不能拿全部题目去问。**

每道题的证据位置（证据出现在哪些天）在 EverMemBench 的 HF 数据集中由一个字段给出，但它不一定和每个批次的题目文件放在一起，可能需要按归一化后的题目文本 join 恢复。**先确认数据集的实际结构，再实现**；恢复不了的题归为 E 类，不要猜。

| 类 | 定义 | 默认是否计分 | 为什么 |
|---|---|---|---|
| A | 证据全部在已灌入的窗口内 | ✅ | 这批语料能回答的题 |
| B | 证据**跨越**窗口边界 | ❌ | **最危险的一类**：检索成功、返回了真实记忆，但材料残缺，模型答错。看起来和"排序缺陷"一模一样，会误导归因 |
| C | 证据全部在窗口外 | ❌ | 必然答不出，计分只会稀释结果 |
| D | 无证据题（反幻觉题，正确答案是"不知道 / 没有发生"） | ✅ | 任何窗口都能判定。但**不同语料规模下的 D 类分数不可比**：库越小，"正确地说不知道"越容易 |
| E | 证据位置无法恢复 | ❌ | 不知道证据在哪 |
| F | 数据集标为范围未知 | ❌ | 一贯排除 |

### 1.4 结局分类（outcome）

每道题的结局先分成**互斥的三类**，再谈对错：

| 结局 | 定义 | 是否计入正确率分母 |
|---|---|---|
| `delivered` | 系统给出了最终答案 | ✅ |
| `undelivered` | 系统运行结束但没有给出最终答案（Agent 层尤其常见：停在"我再查一下……"这类过程性旁白上） | ❌，单独报告比例 |
| `env_failure` | 基础设施故障（服务不可达、超时、限流、数据库错误等） | ❌，单独报告；**绝不算作答错** |

**为什么**：把"没交付"和"环境坏了"算成答错，会让被测系统背锅，也会掩盖"不交付"这个本身更严重的问题。HTTP 200 不等于用户拿到了答案。

**"交付"的判定要从两个方向防错**：
- 过程性旁白不是答案：只认交付动作（例如 `final_answer`）产出的内容。
- **交付动作产出的也不一定是答案**：系统可能先用交付动作发一句**确认或占位语**（"收到，稍后汇报"），真正的答案之后才来。答案没来时，留下的只有这句确认。这种情况要记为 `undelivered`（或者在原因是基础设施时记为 `env_failure`），不能记为 `delivered`。
- 如果"取最后一条交付"，要意识到最后一条可能只是确认。

**两个指标并列报告**：

| 指标 | 定义 | 回答的问题 |
|---|---|---|
| 答案正确率 | 答对 / `delivered` | 答出来的东西对不对 |
| 端到端成功率 | 答对 / (`delivered` + 被测系统自身原因的 `undelivered`) | 用户问了之后，最终拿到正确答案的比例 |

`env_failure` 两个指标都不计入，单独报告。

### 1.5 判分

- **选择题**：确定性地从答案里提取选项字母。提取不唯一时（答案里出现多个字母，或者需要在长文本里"搜"出字母）**打上 `ambiguous_extraction` 标记**，报告里单独统计，不要静默取第一个。
- **开放题**：LLM 评分员，输出 `CORRECT` / `WRONG` 加一句理由。
  - **v1（基线口径）**：宽松匹配，只要包含关键信息就算对；日期允许 ±1 天。
  - **v2（改进口径）**：在 v1 基础上增加**拒答规则**：gold 是"不存在 / 没有参与 / 没有发生"时，"找不到相关记录 / 无法确认"判为 CORRECT；并收紧"宽松"的边界（答案同时给出正确和错误信息时判 WRONG）。
    - **否定类 gold 的关键信息只有"没有发生"这一点。** 这类 gold 常常附带背景（"他没参与，那段时间他在做另一件事"），宽松的评分员会把背景也当成必须复述的关键信息，于是把正确的拒答判错。v2 要明确：背景不要求复述。
    - **拒答之后又给出实质答案，包括带保留措辞的"推断"，判 WRONG**；拒答时列出明确标注为"仅供参考、不是所问答案"的相关记录，判 CORRECT。
  - 两个口径**并行报告**，v1 不被覆盖。
- 评分员调用的温度设为 0；结果缓存（以题目 + 答案 + prompt 版本 + 模型为键），避免重复花钱。
- **评分员的调用代码本身也要测**：
  - **调用失败 ≠ 判错。** 重试耗尽后返回 `False` 的写法，会把一次超时静默记成 WRONG，事后无法分辨。调用失败要报错，计分时拒绝缺少判分的条目。
  - **保存每条判分的原始回复和理由**，否则校准时无法复查。
  - 比较两个口径时，模型、provider、temperature、system prompt 都保持一致，**让 prompt 成为唯一的变量**。

### 1.6 评分员校准

**要回答的问题**：评分员的结论和人的判断一致到什么程度？不一致集中在哪？

1. 从已交付的开放题答案里抽 40–60 条，导出**盲标表**：题目、gold、答案；**隐藏评分员的结论，也隐藏题号**（标注人可能记得某个题号对应的结论）；用固定种子打乱顺序；**保留题型**（细则依赖它）；记录每条答案的哈希，计分时核对答案单元格没有被表格软件改动。
2. **先写标注细则，再开始标**（`docs/judge_rubric.md`）：CORRECT 的定义、拒答怎么判、拒答后又给答案怎么判、部分正确怎么判、多个候选怎么判、口径或单位不同怎么判、日期容差。**标注期间不改细则**；遇到没覆盖的情况，先填 `UNSURE` 并写原因。
3. 人工标注。如果有第二位标注人，计算**人与人之间**的 Cohen's κ；没有的话，隔一周在重新打乱的空白表上自己重标，计算自身前后一致性，并在报告里注明这是较弱的证据。
4. **裁决分歧**：裁决结果单独存档。**人与人的一致性用原始标签计算**，裁决只用于构成和评分员对比的基准。如果因此补充了细则的澄清条款，写明是标注完成之后补的。
5. 计算 人 vs 评分员 v1、人 vs 评分员 v2 的 κ、一致率和混淆矩阵，**并按题型拆分**：总体 κ 可能看起来不错，而某一类题上的系统性偏差被平均掉了。对每个裁决项做**敏感性检查**（翻转后结论变不变）。
6. **逐条给不一致的样本归因**：拒答口径 / 过度宽松 / 格式 / gold 本身有问题 / 人工标错。
7. **稳定性**（可选）：每个口径跑 3 次，报告**翻转率**（同一条答案三次结论不一致的比例）。
8. **警惕"在训练集上测"**：如果 v2 的规则是从这批样本的分歧里总结出来的，在同一批样本上测得的提升是**乐观估计**。要证明能推广，需要一批没参与改写 prompt 的留出样本。**不要为了消除最后一两条分歧继续调 prompt**，尤其是人与人之间本来就有分歧的那几条。

人与人 κ 低于 0.6 时，先改细则再继续：人工标签本身不可靠，校准评分员就没有意义。

**人工标注必须由作者本人（或其他人）完成，AI 不得代标。**

### 1.7 统计口径

| 场景 | 方法 | 为什么 |
|---|---|---|
| 单个比例（如正确率 6/11） | **Wilson 区间** | 小样本下正态近似会给出越界或过窄的区间 |
| 复合指标、差值 | bootstrap（按题重采样，≥ 2000 次，固定随机种子） | 不依赖分布假设 |
| **同一批题上两个 arm（或修复前后）的对比** | **McNemar 精确检验**（只看结论不一致的配对） | 题目是配对的；用两个独立比例相减会丢掉配对信息、夸大不确定性 |
| 一致性 | Cohen's κ + bootstrap 区间 | 一致率会被类别不平衡抬高 |

报告规则：
- 每个比率都带 95% 区间和分母（`6/11 = 55% [28%, 79%]`）。
- 两个 arm 之间的差异，没有通过配对检验就**不说"更好"**，只说"未观察到显著差异"。
- 样本小于 30 时，在表格旁边明确标注"仅供定性参考"。
- **事先算清楚样本量能说明什么。** McNemar 精确检验下，n 个结论变化的配对全部朝同一方向时，p = 2 × 0.5ⁿ：n = 6 时约 0.031，n = 5 时约 0.063。也就是说，**少于 6 道题的回归，无论结果多好都达不到 0.05**，只能做定性验收（"这个 case 修没修好"），不能声称"正确率提升了 X%"。把这张表写成单元测试固定下来。
- **按维度拆分后的小格子不做横向比较**：区间横跨大半个 0–100% 的格子，只能用来定位问题。
- 统计函数要用手算值或教科书例子写单元测试：错一点的统计函数不会报错，只会输出一个看起来正常的区间。

### 1.8 按维度拆分

总分之外，至少按以下维度拆分报告：

1. **题型**（题号前缀：单跳、多跳、时间计算、反幻觉、偏好类等）。**不同题型不能混在一起比较**：例如选择题有随机正确的下限，开放题没有。"有检索结果的题 vs 没有检索结果的题"这种对比，如果两组题型构成不同，比较的其实是题型而不是检索。
2. **检索 × 判分 2×2**：检索命中证据 / 未命中 × 答对 / 答错。四个格子分别对应不同的改进方向：
   - 未命中且答错 → 检索问题；
   - 命中但答错 → 阅读或推理问题；
   - 未命中但答对 → 猜对了，或者靠常识，这部分分数不能归功于记忆；
   - 命中且答对 → 真正由记忆带来的正确。
3. **证据范围**：单群 / 跨群 / 无证据。

归因时的三个提醒：
- **同一个能力可能有多条通路**（例如记忆既可以预先注入 prompt，也可以由 Agent 调用检索工具获取）。只测一条通路得出的"检索为空"结论只对那一条成立。
- **"输入里有材料" ≠ "做过检索"**：要看运行轨迹，不能看输入推断。
- **结局对、过程错**：答案判对了，但走的是错误的路径（例如本该检索记忆，却去搜了公网、恰好得出"找不到"）。端到端分数看不出来，要靠轨迹断言（见 2.3 第 6 项）。

### 1.9 查询形态敏感性实验

**假设**：同一道题，查询的写法会显著影响检索结果（例如把选择题的长选项拼进查询，可能导致检索质量骤降，甚至返回空）。

对每个 arm，同一批题用三种查询各检索一次：① 只用题干；② 题干 + 全部选项；③ 人工改写的短查询。比较三种情况的**证据命中率**和**空结果率**。

这是一个鲁棒性测试：真实用户的提问形态千差万别，检索质量不应该对查询长度极端敏感。结果如实报告，不预设结论。

### 1.10 基线与回归

- **冻结基线**：把一次完整运行的逐题结果（结局、判分、检索是否命中证据、元数据）写成 `baselines/<name>.json`。已存在的基线拒绝覆盖。
- **逐题 diff**：新结果与基线比较，每道题归为 `fixed`（错 → 对）、`regressed`（对 → 错）、`unchanged`、`not_measured`（本轮该题没有测到，例如环境故障）。
- **拒绝不可比的比较**：`corpus_id` 或判分口径不同时拒绝 diff，除非显式传参，并在输出里标红说明。

### 1.11 环境探针

- **前置探针**：检查 LLM 服务可达、记忆服务可达且可写、语料仍在（对一道已知能检索到内容的题跑一次检索）。
- **上游红，下游不跑**：例如记忆服务不可达时，"语料还在"这一项标记为"未运行"，而不是"失败"。一个分不清自己坏了还是上游坏了的探针，比老实承认"没测"更糟。
- **后置探针**：运行结束后再跑一次。后置探针变红，整轮结果标记为 `not_measured`。故障可能发生在运行中途，前置探针挡不住。
- **"能连上"不等于"能用"**：数据库探针要检查**可写**，而不只是 `SELECT 1`。只读故障时读一直正常，只检查连通性的探针会一路亮绿灯。
- **探针的成功判据要和收集逻辑完全一致**：直接调用同一个判定函数，而不是另写一份。否则探针可能在你正要测量的那种故障下亮绿灯。

### 1.12 污染与隔离

- **测量本身可能写入被测系统。** 对记忆系统来说，提一个问题本身就可能被存成记忆；下一次检索时，系统会把提问者自己的问题检索回来，挤掉真正的语料。
- 因此：
  - 检索的判据用"**是否命中语料里的证据**"（例如条目日期落在语料的时间范围内），而不是"返回是否非空"——提问者自己的问题就能让结果非空；
  - **纯检索类的测量用从没提过问的干净身份**：检索本身不写入，一个干净身份可以测完整批题；
  - 会写入的测量，身份是**消耗品**：记一本台账，显式划掉用过的，不要让脚本"自动挑一个没用过的"。
- 本项目的公开 arm（null、bm25、mem0、EverOS）同样适用：每轮 live 运行使用独立的 user_id / 命名空间，并记录在结果元数据里。

## 第二部分：Agent 层评测

### 2.1 被测对象：极简 Agent

**刻意做得很小**，目的是展示"会测什么"，不是做一个好用的 Agent。

```
用户问题
  → 路由（router）：判断问题类型 → memory / web / chitchat
  → 循环（最多 max_iterations 轮）：
       LLM 决定下一步：调用工具 或 给出最终答案
       工具：memory_search(query) / web_search(query) / final_answer(text)
  → 结局：调用了 final_answer = delivered；
          用完预算或只输出文本就结束 = undelivered；
          异常 = env_failure（工具或 LLM 的基础设施错误）或 agent_error（Agent 自身代码出错，单独计）
```

- 预算：`max_iterations`、`max_tool_calls`、`max_same_tool_streak`（同一个工具连续调用的上限）、`wall_clock_s`。
- `memory_search` 背后接 1.1 的任意 arm。`web_search` 是桩：对内部问题返回空，对常识问题返回预置结果。
- LLM 有两种实现：
  - **ScriptedLLM**：确定性的，按"策略"生成行为，用于离线测试和 CI。至少实现以下策略：
    - `good`：先检索记忆，再作答；
    - `stubborn_searcher`：一直换措辞检索，从不作答（模拟不收敛）；
    - `skips_memory`：不检索就直接作答（模拟幻觉风险）；
    - `narrator`：只输出"让我再查查"这类旁白，不调用 `final_answer`；
    - `misrouted`：把记忆类问题路由给 `web_search`，零命中后不回退；
    - `acknowledger`：用 `final_answer` 发出一句确认（"收到，稍后汇报"），之后不再产出答案（对应 1.4"交付工具发出的不一定是答案"）。
  - **OpenAICompatLLM**：真实模型，用 function calling，只在 `live` 测试中使用。

### 2.2 追踪（tracing）

自己实现一个轻量 span 追踪器（不要一开始就依赖外部服务）：

- span 类型：`run` / `route` / `llm_call` / `tool_call`；
- 每个 span 记录：开始和结束时间、父 span、属性（模型、token 数、工具名、参数摘要、返回条数、错误）；
- 流式 LLM 调用额外记录 **TTFT**（首 token 时间）；
- 导出为 JSON；可选导出到自托管的 Langfuse（放到最后做，不是必需项）。

### 2.3 Agent 层的测试维度

每个维度对应 `tests/agent/` 下的一个测试模块，默认用 ScriptedLLM 离线运行。**断言要写成业务语义**，不要只断言"没报错"。

| # | 维度 | 测什么 | 示例断言 |
|---|---|---|---|
| 1 | **交付** | 结局分类是否正确；HTTP 或函数正常返回 ≠ 交付；交付动作发出的确认语 ≠ 交付 | `narrator` 和 `acknowledger` 策略的结局都是 `undelivered`，不是 `delivered` |
| 2 | **收敛与预算** | 预算是否真的生效；不收敛能否被检测出来 | `stubborn_searcher` 在 `max_tool_calls` 内停止；`budget_hit=True`；`max_same_tool_streak` 被记录 |
| 3 | **路由** | 路由的准确率；混淆矩阵 | 在标好类别的题集上，输出每个类别的 precision/recall；记忆类问题被路由到 web 的比例。**期望标签优先取被测系统自己声明的规则**（例如"需要检索历史对话的问题必须走能检索记忆的通道"），这样判定不依赖评测者的主观；一条消息触发多次路由时，以**第一次**的决定为准。看路由的**后续行为**（是否真的调用了对应工具），不只看标签 |
| 4 | **回退** | 主路径零命中时是否回退 | `misrouted` 策略下，web 零命中后应回退到 `memory_search`；不回退时标记为"路由失败导致的幻觉风险" |
| 5 | **工具故障注入** | 工具超时、返回空、抛异常、返回格式错误时的行为 | 记忆工具超时 → 结局是 `env_failure` 或者重试后成功，**不能**是一个看似正常的答案 |
| 6 | **轨迹断言** | 工具的调用顺序和约束；**结局对、过程错**也要抓出来 | 记忆类问题：`final_answer` 之前必须至少有一次 `memory_search`；`skips_memory` 策略违反该断言，**即使它的答案恰好判对** |
| 7 | **反幻觉** | 无证据题是否拒答 | 在 D 类题上统计拒答率；`skips_memory` 策略的拒答率应明显更低 |
| 8 | **trace 完整性** | 观测数据本身是否可信 | 每个工具调用都有对应的已关闭 span；子 span 的时间范围落在父 span 内；span 数 = 实际步数 |
| 9 | **耗时拆解** | 端到端耗时由什么组成 | 报告 `llm`、`tool`、`framework`（= 总耗时 − LLM − 工具）三段的占比；流式调用报告 TTFT |

关于第 9 项，Agent 端到端耗时的瓶颈**不只有"推理"和"外部工具"两种**：框架本身（轮次之间的调度、上下文组装、token 计数、序列化）也可能占很大比例。所以要单列 `framework` 一段，而不是只拆两段。

### 2.4 Agent 层的离线评测运行

除了逐条的测试用例，还要能对一个题集批量运行 Agent，产出与记忆层同格式的结果文件，外加每题的 Agent 指标：
`outcome`、`n_llm_calls`、`n_tool_calls_by_name`、`budget_hit`、`max_same_tool_streak`、`route`、`latency_breakdown`、`ttft_ms`。

报告里加一节 Agent 指标，至少包括：交付率、预算触发率、各工具调用次数的分布、路由混淆矩阵、耗时拆解。

## 第三部分：测试工程

### 3.1 pytest 插件 `pytest_agenteval`

| 功能 | 机制 | 语义 |
|---|---|---|
| `@pytest.mark.requires_env("llm", "memory_service", "corpus")` | `pytest_configure` 注册 marker；session 开始时跑一次探针并缓存；`pytest_runtest_setup` 里探针不通过就 skip 并写明原因 | 对应 1.11：上游红，下游跳过 |
| 后置探针 | `pytest_sessionfinish` | 后置变红时，在终端摘要和 JSON 报告里把整轮标为 `not_measured` |
| `--eval-baseline <path>` | `pytest_addoption` + fixture | 逐题 diff，终端摘要（`pytest_terminal_summary`）输出 fixed / regressed / unchanged / not_measured 的计数 |
| `--eval-qids <file>` | `pytest_generate_tests` | 每道题生成一个用例，用例 id 就是题号 |
| `--live` | `pytest_addoption` + `pytest_collection_modifyitems` | 没传时，所有 `live` 用例都跳过 |
| 插件自测 | pytester | 覆盖：探针红时跳过、后置探针红时整轮 `not_measured`、diff 的四种结局、`--live` 开关 |
| **探针做成自定义 hook** | 单独的 hookspec 模块 + `pytest_addhooks` 注册 `pytest_agenteval_probes(config, keys, phase)`（`firstresult=True`）；插件自带 `trylast` 的默认实现 | 自测时在 conftest 里实现同一个 hook，换成假探针；**插件还要强制执行"上游红，下游未运行"**，即使 hook 实现谎报下游正常 |
| **门禁先于 fixture** | `pytest_runtest_setup` 标 `tryfirst=True` | 否则一个访问失效服务的 fixture 会让用例 ERROR，而不是跳过 |
| **数据获取中途失败 → 未测到** | 提供 `not_measured(request, reason)` 辅助函数，fixture 调用它来跳过并记录 | 前置探针是绿的、运行中途服务失效时，受影响的用例记为"未测到"，**不报 ERROR**，也不把整轮作废 |
| **未知的探针名 / 不可比的基线** | 抛 `pytest.UsageError` | 拼错的探针名不能被当成"未运行"静默跳过 |

插件放在独立目录，通过 `-p pytest_agenteval` 或 `pyproject.toml` 的 `pytest11` entry point 加载。

**验收用例要先测试它自己**：每条验收判据都应该在一个已知有缺陷的输入上运行并**失败**。本项目里，ScriptedLLM 的坏策略（`stubborn_searcher`、`skips_memory`、`narrator`、`misrouted`、`acknowledger`）就是这些已知有缺陷的输入。一条在坏策略下也能通过的判据，区分不了"修好了"和"没修好"。

**判据要防假修复**：如果"修复"只是把上限调小，"更快、更少调用"之类的指标都会改善，答案却照样是错的。所以速度、次数类的判据，必须和"答对"一起要求。

### 3.2 Allure 的用法

不要只是"生成一份 Allure 报告"，要用到它能体现测试组织能力的部分：

| Allure 功能 | 用在哪里 |
|---|---|
| `epic` / `feature` / `story` | epic = 记忆层 / Agent 层 / 框架自测；feature = 测试维度（交付、收敛、路由……）；story = 题型或策略 |
| `severity` | 交付、反幻觉、故障注入类用例设为 critical |
| `allure.dynamic.title` / `description` | 参数化用例的标题写成"题号 + 题型 + 被测 arm" |
| `allure.attach` | 附上：Agent 的 trace JSON、最终答案、评分员的理由、检索返回的前几条 |
| `allure.step` | Agent 用例把 路由 → 每一轮 → 结局 写成步骤 |
| `environment.properties` | 写入 corpus_id、arm、模型、评分员口径、git commit |
| `categories.json` | 把失败分类：产品缺陷 / 测试缺陷 / 环境故障（对应 1.4 的结局分类） |
| 历史趋势 | CI 发布到 GitHub Pages 时保留 history 目录，展示多次运行的趋势 |

### 3.3 两种报告的分工

| 报告 | 回答的问题 | 生成方式 |
|---|---|---|
| Allure 测试报告 | 用例通过了没有？失败在哪？ | allure-pytest |
| 评测报告 | 各系统表现如何？差在哪？结论可信吗？ | Jinja2 静态 HTML：总表（带区间）、按题型拆分、2×2、评分员校准、Agent 指标、逐题明细 |

两份报告都发布到 GitHub Pages，从 README 链过去。

### 3.4 工程纪律

- **按 ID 关联，永远不按位置。** 某些评测库会先返回所有选择题、再返回所有开放题，按位置拼接会把每个结论贴到错误的题目上，算出的总分却看起来很正常。
- **结果文件拒绝被覆盖**：冻结的基线、已经填了标签的标注表，覆盖都需要显式参数。
- **平台相关的全局设置在模块导入时完成**，不要放进协程里懒加载。例如 Windows 上异步数据库驱动需要的事件循环策略，等事件循环已经创建再设置就晚了。
- **数据库连接池会绑定到打开它的事件循环**：多次 `asyncio.run` 之间要先关闭连接池；能用子进程隔离的（例如探针），就用子进程。
- **重试不能静默。** "第一次失败、第二次成功"必须发出警告：环境偶发故障是这个样子，**确定性的 bug 也是这个样子**。
- **报告里的数字由代码生成**；发现错误时**在原处更正**，写明日期、原来写了什么、为什么错，不悄悄改掉。
- **每份报告都有"局限"一节**，放在结论附近。
- **根因描述要用原始数据核对**，不能只依据摘要或 trace 汇总里的说法。

## 第四部分：反模式速查与发布前自检

### 4.1 反模式

| 反模式 | 症状 | 对策 |
|---|---|---|
| 按位置关联结果 | 数字偏一点，不报错 | 按 ID 关联（3.4） |
| 用"非空"代替"命中" | 污染让所有题看起来都正常 | 用"命中证据"作判据（1.12） |
| 调用成功 / 发出了交付 = 交付成功 | 旁白、确认语被当成答案 | 双向判定（1.4） |
| 环境故障算成被测系统失败 | 分数凭空下降，查不出原因 | `env_failure` 单列，后置探针（1.11） |
| 只看总体一致性 | 某一类题的系统性偏差被平均掉 | 按题型拆分 κ（1.6） |
| 评分员调用失败记成判错 | 评分员"偏严"其实是网络问题 | 失败报错，保存回复（1.5） |
| 在调参的样本上评估 | 改进幅度被高估 | 留出集，注明乐观估计（1.6） |
| 小样本给精确百分比 | 读者以为差几个点有意义 | 带区间，事先算统计能力（1.7） |
| 混杂分组对比 | 比的是题型，不是能力 | 按题型拆分后再比（1.8） |
| 验收判据在缺陷输入上也通过 | 区分不了修好和没修好 | 先在坏策略上跑（3.1） |
| 只测一条通路 | 结论只对一半成立 | 列出全部通路（1.8） |
| 只看结局 | 过程错误被掩盖 | 轨迹断言（2.3） |
| 静默重试 | 确定性 bug 看起来像偶发故障 | 重试成功也要警告（3.4） |

### 4.2 发布前自检

**口径**
- [ ] 被测对象、结局分类、计分范围（哪些题、为什么）写清楚了
- [ ] 有对照组（null arm），或者说明了没有对照时绝对分数能说明什么
- [ ] 列出了污染来源，并说明是怎么排除的

**数据**
- [ ] 所有关联都按 ID，没有按位置
- [ ] 结果文件带元数据；对比的两份数据元数据一致
- [ ] "交付"的判定两个方向都检查过
- [ ] 前置和后置探针都是绿的；环境故障单独计数

**判分**
- [ ] 评分员在这类题上校准过，或者注明了没有校准
- [ ] 评分员调用失败不会被记成判错
- [ ] 改过的口径和原口径并行报告

**统计与结论**
- [ ] 每个比率都带分母和区间
- [ ] 对比用了配对检验；没有显著差异就不说"更好"
- [ ] 没有在混杂分组之间直接比较
- [ ] 至少用一个独立数据源交叉核对过每条主要结论
- [ ] 写了"局限"一节
